# 02 — Concepts

This page defines every idea the rest of the documentation uses. Read it once;
after that the API reference will read like a dictionary.

## The one-sentence model

> A Roblox game **emits** typed **events**; ClientBridge validates them and
> publishes them through one or two **channels**; external tools **read** them.

There is no path from a tool back into the game.

## Event

An **event** is one immutable fact the game wants the outside world to know:

- `biome` changed to *Glitch*;
- player obtained aura *Chromatic* with rarity 75,000,000;
- a 2x luck boost started and ends at a given time.

Events are facts, not commands: past tense, no “please do X”. This is what
keeps the bridge read-only.

Each event has:

| Field | Meaning |
|---|---|
| `type` | the event kind, e.g. `biome` |
| `data` | the declared payload, e.g. `{ name = "Glitch", endsAt = 1762000300 }` |
| `scope` | who the event belongs to: everyone (`server`) or one player (`player`) |
| `origin` | who reported it: the game server (`server`) or a client (`client`) |

## Envelope

The **envelope** is the standard wrapper the module adds to every event before
anything leaves the game:

```json
{
  "id": "4aa1af3c-7769-45fc-930e-fc378af8fa96",
  "type": "biome",
  "at": 1762000000,
  "scope": "server",
  "origin": "server",
  "data": { "name": "Glitch", "endsAt": 1762000300 }
}
```

| Key | Type | Notes |
|---|---|---|
| `id` | string | unique per event, generated by the server |
| `type` | string | lowercase, `[a-z0-9_.-]`, 1–32 chars |
| `at` | integer | epoch seconds from the server clock |
| `scope` | `"server"` / `"player"` | see below |
| `origin` | `"server"` / `"client"` | who reported it |
| `data` | object | declared fields only |
| `session` | string | **only** on player events in the HTTP channel |

Tools should use `id` to de-duplicate, `at` to sort, and `type` to route.
The envelope is frozen by [protocol 1](06-protocol-v1.md); new fields would be
added only in a new protocol version.

## Scope

Scope answers *“who is this event about?”* and decides delivery:

| Scope | Console channel | HTTP channel |
|---|---|---|
| `server` | sent to **every** connected client | queued without a session token |
| `player` | sent **only to that player's client** | queued **only if** that player opted in, tagged with their token |

A server-scoped event is public (biome changes, global timers). A player-scoped
event is private (their roll, their inventory) and is never broadcast to other
players.

The declared schema decides the scope:

```lua
events = {
	biome = { scope = "server", data = { ... } },  -- broadcast
	roll  = { scope = "player", data = { ... } },  -- per player
}
```

`emit(type, data)` uses the declared scope. `emitTo(player, type, data)`
**always** forces `player`, even if the declared scope says otherwise — that is
a safety rule: asking for per-player delivery can never leak to everyone.

Events emitted by a client with `ClientBridge.emit` are always `scope = "player"`
and `origin = "client"` (see [Origin](#origin)).

## Origin

Origin answers *“can I trust this?”*

| Origin | Meaning | Trust |
|---|---|---|
| `server` | produced by a `Script` in `ServerScriptService` | trusted: server code is authoritative |
| `client` | reported by the LocalScript of one player | **not trusted**: the client can lie |

The module never pretends a client event is trusted. If you build a tool that
cares about accuracy, filter `origin == "server"` or treat client events as
hints. Server owners can turn client events off entirely:

```lua
ClientBridge.start({ allowClientOrigin = false, ... })
```

## Channel (transport)

A **channel** is a way to get events out of the game. Both can be on at once.

| | Console | HTTP |
|---|---|---|
| Setup | none | endpoint + opt-in + HTTPS |
| Where events go | the player's own client log | your server (via `HttpService`) |
| Works in Studio | yes | yes (localhost only) |
| Works in a published game | yes | yes |
| Needs `Allow HTTP Requests` | no | yes |
| Cross-player | server scope only | server scope, plus opted-in players |
| Tool needs the game open | yes (reads the log) | no (reads your API) |
| One-way | yes | yes |
| Default | **on** | **off** |

The console channel is what makes the project zero-setup: a tool tails the log
and parses `[CLIENTBRIDGE:1]` lines. The HTTP channel is what makes it work
without the game running on the tool machine.

## Opt-in

Roblox’s rules make one player’s data different from public game data. The
HTTP channel therefore requires the **player** to opt in before any
player-scoped event leaves the server:

```lua
-- inside your UI, triggered by a button the player pressed
ClientBridge.optIn()
```

Server-side, `ClientBridge.optIn(player)`:

1. asks `PolicyService` whether this player is allowed to see external links;
2. creates a random session token, valid for 24 hours by default;
3. sends the token to that player’s client;
4. tags subsequent player-scoped HTTP events with that token.

Opting out (`ClientBridge.optOut()` / `optOut(player)`) revokes the token
immediately. Leaving the game, or the token expiring, does the same.

The player’s token is a **bearer credential**: whoever has it can read that
session’s events. The design assumes the player chooses to hand it to a tool.

## Session token

```text
cb_0123456789abcdef0123456789abcdef
```

- `cb_` prefix + 32 lowercase hex characters (a GUID without dashes);
- random, unguessable, not derived from `UserId` or the player’s name;
- created only by an explicit opt-in;
- expires after `session.ttlSec` (default 24 h);
- one active token per player; a new opt-in replaces the old token;
- mapped to the player only inside the server module — `UserId` never leaves.

Tools receive the token out-of-band (the player copies it from the game UI)
and use it against **your** API. See
[the read contract](06-protocol-v1.md#read-contract).

## Schema

A **schema** is the per-event contract declared in `start`:

```lua
events = {
	biome = {
		scope = "server",
		data = {
			name = "string:24",   -- string with at most 24 characters
			endsAt = "number",    -- finite number
		},
	},
}
```

It does three jobs:

1. **Documentation** — readers of `start` know exactly what each event means.
2. **Validation** — undeclared fields, wrong types and over-long strings are
   rejected before anything is sent (returns `false, reason`).
3. **Size control** — the event cannot exceed the configured byte budget.

Declaring `events` is optional. Without it, a generic validation applies:
flat object, at most 24 keys, strings ≤ 64 chars, finite numbers and booleans.
Declaring is strongly recommended for anything public.
Full grammar: [Event schema](05-event-schema.md).

## Redaction

Even a correct schema can carry personal data. Before sending, the **Redactor**
scans every value and key and refuses:

- keys such as `username`, `email`, `phone`, `userid`, `chat`, `discord`, `ip`;
- strings longer than 64 characters;
- strings that look like e-mail, URLs, Discord tags, IPv4, CPF or phone numbers.

Blocked events are counted and audited (metadata only), never sent. Details:
[Security & privacy](09-security-privacy.md).

## Audit, metrics

- **Audit** is a 200-entry ring of metadata: start, stop, blocked events,
  opt-in/out, HTTP drops. It never stores field values.
- **Metrics** is a snapshot of counters: emitted, blocked, console deliveries,
  HTTP deliveries, queue size, failures.

Both are read from the server; see
[API reference](03-api-reference.md#metrics-and-audit-shapes).

## Validation pipeline

This is the whole life of an event:

```
emit(type, data)
   │
   ├─ started?  ──────────────── no → false, "not_started"
   ├─ enabled?  ──────────────── no → false, "disabled"
   ├─ data is a table?  ──────── no → false, "invalid_table"
   ├─ Schema.validateEvent ───── no → false, reason (audited, blocked++)
   ├─ Redactor.check ─────────── no → false, reason (audited, blocked++)
   ├─ Json.encode + size check ─ no → false, "event_too_large"/"encode_error"
   │
   └─ dispatch
        ├─ console → client prints "[CLIENTBRIDGE:1] {…}"
        └─ HTTP    → queue → batched POST (opt-in rules apply)
```

Everything that fails ends in `blocked` + an audit entry. Nothing is sent.

## One-way by design

There is no endpoint in the module, no listening socket, no command handler.
The client can only say “emit this player event” or “opt me in/out”; the server
never executes tool input. That is a deliberate security boundary, not a
missing feature.

## What ClientBridge is not

| Not this | Why |
|---|---|
| Memory reader / executor | those are exploits; the bridge only handles data the game chooses to publish |
| Command RPC | tools cannot control the game; no inbound path exists |
| Anti-cheat | it does not detect or enforce anything |
| Cross-server bus | events travel to external consumers, not to other Roblox servers |
| Analytics platform | it only moves events; storage/analysis belongs to your backend |

## A mental model

Think of ClientBridge as a **press release desk** inside the game:

- game code files a press release (`emit`);
- the desk checks the form (schema), removes private information (redaction)
  and assigns it a number (`id`);
- the public channel pins it on a board every player can read (console);
- the private channel mails it only to subscribers (opt-in HTTP);
- reporters (tools) read the board or their mail; they cannot call the desk.
