## Versioning and the two tags

There are two version markers:

| Marker | Where | Meaning |
|---|---|---|
| `:1` | console prefix `[CLIENTBRIDGE:1]` | console line format |
| `"v": 1` | HTTP batch body | HTTP batch format |
| `X-ClientBridge-Version: 1` | HTTP header | same version, for routing |

`ClientBridge.PROTOCOL = 1` in Luau. A breaking change bumps both the console
tag and the HTTP `v` (and the header). Non-breaking additions (for example a new
optional response field) may appear without a bump; consumers must ignore
unknown fields. See [Versioning](17-versioning.md).

## Event envelope

Every event becomes this object:

```json
{
  "id": "4aa1af3c-7769-45fc-930e-fc378af8fa96",
  "type": "biome",
  "at": 1762000000,
  "scope": "server",
  "origin": "server",
  "data": { "name": "Glitch", "endsAt": 1762000300 }
}
```

| Field | Type | Rules |
|---|---|---|
| `id` | string | GUID generated by the Roblox server; unique per event; used for de-duplication |
| `type` | string | `^[a-z0-9_.-]{1,32}$` |
| `at` | integer | epoch seconds, server clock |
| `scope` | `"server"` \| `"player"` | who the event belongs to |
| `origin` | `"server"` \| `"client"` | trust level |
| `data` | object | declared fields only, flat |
| `session` | string | **only** in the HTTP channel, **only** for player events with an active opt-in |

`session` is added by the HTTP layer when the event is queued, not part of the
console envelope and not part of the event as produced by game code.

## Canonical JSON

The module serializes with its own encoder to guarantee exact bytes across
platforms. The rules:

1. **Objects**: keys sorted in UTF-8 byte order; no whitespace.
2. **Arrays**: original order; no whitespace.
3. **Strings**: `"` and `\` escaped; `\b \f \n \r \t` use short escapes; other
   control characters use `\u00xx` (lowercase hex); everything else (including
   non-ASCII) is emitted as UTF-8 bytes unchanged.
4. **Numbers**: formatted like C’s `%.14g` — no trailing `.0`, no unnecessary
   digits, exponent form for very large/small values. `NaN`/`∞` would be
   invalid and are rejected before encoding.
5. **Booleans/null** as usual.

Example — this Luau table:

```lua
{ b = 1, a = { name = "Glitch", endsAt = 1762000300 } }
```

becomes:

```json
{"a":{"endsAt":1762000300,"name":"Glitch"},"b":1}
```

### Why this matters

The HTTP signature signs this exact byte sequence. A backend that re-encodes
with a generic JSON library will usually match for simple data, but **not
guaranteed** for floats and Unicode. If you verify signatures in another
language, implement the same rules (the reference API has a
`canonical_json()` function you can port).

## Channel 1 — console line

Format:

```text
[CLIENTBRIDGE:1] {canonical JSON envelope}
```

- fixed prefix, one space, then the envelope;
- exactly one line per event, terminated by `\n` in the log;
- printed by the **client**, so it lands in the player’s own log;
- maximum 8192 bytes (`line_too_large` blocks bigger events);
- no `session` field.

Example:

```text
[CLIENTBRIDGE:1] {"at":1762000000,"data":{"endsAt":1762000300,"name":"Glitch"},"id":"4aa1af3c-7769-45fc-930e-fc378af8fa96","origin":"server","scope":"server","type":"biome"}
```

Delivery rules:

| Scope | Who receives and prints |
|---|---|
| `server` | every connected client (`Remote:FireAllClients`) |
| `player` | only that player’s client (`Remote:FireClient`) |

Parsing guidance:

- match the prefix with a literal string, then parse the rest as JSON;
- if JSON parsing fails, ignore the line (partial writes are rare but possible);
- de-duplicate by `id`;
- do not assume key order beyond the canonical rule; use a JSON parser.

## Channel 2 — HTTP batch

The module queues envelopes and POSTs them in batches.

### Request

```http
POST /clientbridge HTTP/1.1
Host: api.example.com
Content-Type: application/json
X-ClientBridge-Version: 1
Authorization: Bearer <secret>        (only when secretName is configured)
```

```json
{
  "v": 1,
  "universeId": 10774290674,
  "placeId": 78552789773801,
  "sentAt": "2026-11-04T12:00:00Z",
  "events": [
    { "id": "...", "type": "biome", "at": 1762000000,
      "scope": "server", "origin": "server", "data": { "name": "Glitch" },
      "session": "cb_..." }
  ],
  "sig": "base64url(hmac-sha256)"
}
```

| Field | Type | Notes |
|---|---|---|
| `v` | integer | must be `1` |
| `universeId` | integer | `game.GameId` (may be `0` in Studio) |
| `placeId` | integer | `game.PlaceId` (may be `0` in Studio) |
| `sentAt` | string | `YYYY-MM-DDTHH:MM:SSZ` (UTC) |
| `events` | array | 1..`batchSize`; each is an envelope, with `session` when player-scoped and opted in |
| `sig` | string? | present only when `signingKey` is configured |

Additional headers:

- `X-ClientBridge-Version: 1` is always sent.
- `Authorization` is sent **only** if `secretName` resolves to a secret. Its
  value is the secret verbatim — store `Bearer <token>` if your backend expects
  a bearer scheme, or the raw token if it does not.
- No cookies, no user agent requirements, no query parameters.

`universeId`/`placeId` are `0` when running in Studio, because the place is not
published. Backends must accept `0`.

### What the module does with the response

The module only distinguishes:

| Response | Meaning to the module |
|---|---|
| `2xx` | accepted; the batch is removed from the queue |
| anything else, timeout, DNS/SSL error | failure; retried on a later flush (no separate backoff timer) |

The response **body is ignored** by the module. The reference API returns JSON
for humans and for direct tooling, but a custom backend may return an empty
`204`.

Batching defaults: up to 100 events per request, flush every 5 s, at most 400
requests/minute (`http.budgetPerMinute`), max 4 retries. See
[Configuration](04-configuration.md#http-options).

## Signature

When `signingKey` is set, the module computes:

```text
canonical = canonical_json({
    v:        1,
    universeId: <int>,
    placeId:    <int>,
    sentAt:     "<UTC ISO-8601>",
    events:     [ <envelope with session if any>, ... ]
})

sig = base64url( HMAC-SHA256( signingKey, canonical ) )     (no "=" padding)
```

Notes:

- the object passed to the canonical encoder has exactly the five keys above,
  in sorted order after encoding (`events`, `placeId`, `sentAt`, `universeId`,
  `v`);
- `sig` itself is **not** part of the signed object;
- the key is a UTF-8 string from the server Script; it never goes over the
  network;
- base64url uses `-` and `_` and omits padding.

### Test vector

Generated inside Roblox Studio with the module’s own `Crypto` and `Json`:

```text
signingKey = test-signing-key

canonical =
{"events":[{"at":1762000000,"data":{"endsAt":1762000300,"name":"Glitch"},"id":"evt_1","origin":"server","scope":"server","type":"biome"}],"placeId":78552789773801,"sentAt":"2026-11-04T12:00:00Z","universeId":10774290674,"v":1}

sig = _450CPheIz4xCH_X7GogCcij5wxeo9NeAMyR-xTH9I8
```

### Verifying in Python

```python
import base64, hashlib, hmac
from clientbridge_api import canonical_json

signed = {"v": 1, "universeId": 10774290674, "placeId": 78552789773801,
          "sentAt": "2026-11-04T12:00:00Z", "events": [...]}
digest = hmac.new(b"test-signing-key", canonical_json(signed).encode(), hashlib.sha256).digest()
expected = base64.urlsafe_b64encode(digest).decode().rstrip("=")
```

Compare with `hmac.compare_digest`, never with `==`.

### Verifying in other languages

Port the canonical encoder, not just HMAC:

- sort object keys by UTF-8 bytes;
- no spaces;
- numbers formatted like `%.14g` (Python: `format(float(v), ".14g")`;
  JavaScript: careful, `Number#toString` differs for some values);
- escape only what the rules above require.

If a signature fails only for some payloads, number or Unicode formatting is
almost always the cause. The reference API’s `canonical_json()` is a tested
port.

## Read contract

The HTTP channel is write-only from the game’s perspective: the game POSTs and
never reads. Tools read from **your** backend. The reference API implements this
contract (a custom backend can implement just this part):

### `GET /sessions/{token}/events`

```http
GET /sessions/cb_0123456789abcdef0123456789abcdef/events?since=0&limit=100
```

| Query | Default | Rules |
|---|---|---|
| `since` | `0` | exclusive cursor; returns events with `seq > since` |
| `limit` | `100` | 1..500 |

Response:

```json
{
  "ok": true,
  "session": {
    "first_seen": "2026-11-04T12:00:00Z",
    "last_seen": "2026-11-04T12:04:10Z",
    "expires_at": "2026-11-05T12:04:10Z",
    "universe_id": 10774290674,
    "place_id": 78552789773801
  },
  "events": [
    { "seq": 41, "id": "…", "type": "roll", "at": 1762000000,
      "scope": "player", "origin": "server",
      "data": { "aura": "Chromatic" },
      "received_at": "2026-11-04T12:04:09Z" }
  ],
  "next": 41,
  "has_more": false
}
```

- `next` is the cursor to pass as `since` on the next request;
- `has_more` is `true` when the backend has more events immediately available;
- the token itself is not echoed in the response;
- **this endpoint returns that player’s private events only.** Public
  (server-scope) events are not included. For a combined global + private
  history, replay the WebSocket stream with `?token=…&since=…` (or use the
  admin feed for global events);
- `404` means unknown/expired/revoked token.

### `DELETE /sessions/{token}`

Revokes the token, deletes that session’s buffered events and closes its live
streams:

```json
{ "ok": true, "revoked": true, "deleted_events": 41, "closed_streams": 1 }
```

The game-side `optOut` is **not** this endpoint: it stops new events and drops
queued ones, but the backend copy of the token remains valid until its TTL (24 h
from opt-in, by default) or until this `DELETE` is called. Tools/players should
call `DELETE` when they want the backend to forget the session.

### Admin feed

`GET /events?since=&limit=&universe_id=&type=` with
`Authorization: Bearer <admin_token>` returns all buffered events, including
`universe_id`, `place_id` and `session`. Disabled unless `admin_token` is set.

> The read contract is **not** part of protocol 1’s frozen surface in the same
> way the envelope is: it is the reference API’s shape. A custom backend may
> serve events differently, as long as its documentation tells tools the URL and
> JSON shape.

## Live stream

The reference API also exposes the same events in real time over WebSocket:

```text
ws://host:port/stream                  public events
ws://host:port/stream?token=cb_...     public + that session's events
```

That contract (handshake, hello, event/error messages, replay cursor,
heartbeat) is documented in [Live streaming](18-streaming.md). The HTTP batch
stays the only ingestion path because Roblox cannot open WebSockets.

## Status codes and error bodies

The reference API uses these codes. The module treats every non-`2xx` as a
failure and retries, so a custom backend should pick codes carefully.

| Code | When | Body `error` |
|---|---|---|
| `200` | batch accepted | — |
| `400` | malformed JSON, wrong types, bad event, wrong version | `invalid_json`, `invalid_payload`, `invalid_event`, `unsupported_version`, `invalid_query`, `invalid_session` |
| `401` | missing/wrong `Authorization` or signature | `unauthorized` |
| `403` | admin feed disabled | `admin_disabled` |
| `404` | unknown endpoint or session | `not_found`, `unknown_session` |
| `409` | exact replay (only with strict replay) | `replay` |
| `411` | no `Content-Length` | `length_required` |
| `413` | body over `max_body_bytes` | `payload_too_large` |
| `415` | wrong `Content-Type` | `unsupported_media_type` |
| `426` | `/stream` without upgrade | `upgrade_required` |
| `429` | rate limit | `rate_limited` (+ `Retry-After`) |
| `500` | internal error | `internal_error` |

Error body shape:

```json
{ "ok": false, "error": "invalid_event", "detail": "type must match ^[a-z0-9_.-]{1,32}$" }
```

## What the module does with a response

Detailed in [Configuration](04-configuration.md#what-happens-when-things-go-wrong),
but the protocol-level rules are:

1. `2xx` → batch accepted, removed from the queue.
2. Non-`2xx`/network error → batch is re-queued at the front if any event still
   has retries left; otherwise dropped and audited.
3. Three consecutive failed requests → 30-second circuit breaker.
4. The module never reads the response body, so a custom backend can answer
   `204 No Content`.
5. `429`/`5xx` should be temporary; `401`/`403` usually mean a configuration
   mistake and will keep failing until fixed.
